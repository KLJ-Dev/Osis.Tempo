# 🕒 Osis.Tempo

**개인의 하루 일정을 계획하고 관리하는 Java/Spring Boot 기반 웹 스케줄 관리 서비스입니다.**

PC와 모바일에서 동일한 일정을 관리하고, 하루의 흐름과 생활 리듬을 체계적으로 관리할 수 있도록 설계한 프로젝트입니다.

## 🧱 4. 아키텍처 설계

### 4.1. REST API 기반 구조

React 프론트엔드와 Spring Boot 백엔드를 REST API로 분리합니다.

PC와 모바일 브라우저는 동일한 백엔드 API를 통해 일정 데이터를 관리합니다.

### 4.2. 역할 분리

백엔드는 다음 계층으로 구분합니다.

| 계층 | 역할 |
|---|---|
| Controller | HTTP 요청 및 응답 |
| Service | 일정 관련 비즈니스 로직 |
| Repository | 데이터 접근 및 영속성 |
| Entity | 데이터베이스 매핑 |
| DTO | API 요청 및 응답 데이터 |

PostgreSQL을 데이터 저장소로 사용하고 Spring Data JPA를 통해 연동합니다.

> 현재 아키텍처는 초기 설계안이며 실제 구현이 완료되었다는 의미는 아닙니다.

### 4.3. AI 협업 원칙

- 작업 전 `README.md` 및 제작지시서를 우선 확인합니다.
- 프론트엔드는 GPT 중심으로 개발합니다.
- Java/Spring Boot 및 PostgreSQL은 사용자가 직접 개발하는 것을 원칙으로 합니다.
- 코드 변경은 별도 브랜치에서 수행하고 Pull Request로 보고합니다.
- PR에는 변경 전후 차이, 수정 이유, 영향 범위 및 테스트 결과를 명시합니다.
- 사용자 승인 전에는 기본 브랜치에 병합하거나 배포하지 않습니다.
- AI는 코드 생성을 지원하되, 코드의 이해와 최종 결정권은 사용자에게 있습니다.

## 🖥️ 5. 프론트엔드 프로토타입 (React + TypeScript)

사용자가 사용하던 엑셀 기록일지의 네 영역을 OSIS.Tempo의 **반응형 대시보드**로 옮긴 초기 화면입니다. 현재는 별도 백엔드와 DB 없이 프론트엔드에서만 동작합니다.

### 기본 화면 배치

| 위치 | 위젯 | 데스크톱 너비 |
| --- | --- | --- |
| 상단 | Today · 오늘 할 일 | 100% |
| 중단 왼쪽 | Tasks · 작업 목록 | 40% |
| 중단 오른쪽 | Upcoming · 다가오는 일정 | 60% |
| 하단 | Notes · 메모 | 100% |

- PC(너비 850px 이상): 10컬럼 기반 **4:6 비율** 기본 배치.
- 모바일: 한 줄씩 표시하고 화면 너비에 맞춰 순서를 변경할 수 있습니다.
- **레이아웃 편집**: 위젯 제목을 드래그해 순서를 바꾸고, 오른쪽 아래를 드래그해 크기를 조절합니다.
- **배치 저장**: 레이아웃을 `localStorage`에 자동 기록해 같은 브라우저 재접속 시 복원합니다. **기본 배치** 버튼은 위젯 배치만 초기화합니다.
- **기본 화면 동작**: 오늘/전체 할 일 체크 연동, 작업 추가, 분류 필터, 메모 편집 및 브라우저 자동 저장.
- Upcoming 일정은 **상대 날짜로 생성하는 샘플 데이터**이며 일정 추가·수정·삭제는 아직 구현하지 않았습니다.
- 레이아웃, 할 일, 메모는 브라우저별 로컬 데이터입니다. **로그인, 여러 기기 동기화, Spring Boot API, PostgreSQL은 미구현**입니다. 브라우저 데이터 삭제 시 저장된 내용이 사라집니다.

### 로컬 실행

Node.js 20 이상 및 npm 설치 후 저장소 루트에서:

```bash
cd frontend
npm install
npm run dev
```

브라우저에서 `http://localhost:5173` 접속합니다. 정적 빌드는 `npm run build`입니다.

### 프론트엔드 파일 구성

```text
frontend/
├── package.json
├── index.html
├── tsconfig.json
├── vite.config.ts
└── src/
    ├── main.tsx
    ├── App.tsx       # 위젯, React 상태, 배치 및 로컬 저장
    └── styles.css    # 반응형 그리드 및 8번 시안 계열 디자인
```

UI 프레임워크는 React 18 + TypeScript + Vite, 위젯 레이아웃은 `react-grid-layout` 1.x의 `Responsive`/`WidthProvider`를 사용합니다.

> **검증 상태:** 소스 구성과 기본 배치, 네 위젯 키, 상태 및 저장 분리 로직의 정적 점검만 수행했습니다. 도구 실행 환경의 npm 레지스트리 DNS 연결 실패로 의존성 설치와 실제 `npm run build`, 브라우저 동작 테스트를 진행하지 못했습니다.

## 🤖 AI 협업 및 코드 변경 관리 원칙

### 1. 개발 지침 우선
- 작업 전 해당 레포지토리의 `README.md`와 존재하는 제작지시서 및 개발 지침을 확인한다.
- 기존 아키텍처, 네이밍 규칙과 코드를 존중하며, 불명확한 사항은 사용자에게 확인한다.

### 2. 채팅 내 Pull Request 형식 보고
- AI는 수정 파일, 변경 전후 차이, 변경 이유, 영향 범위, 검증 및 테스트 결과를 **채팅에서 Pull Request 형식으로 보고**한다.
- 위 보고는 실제 GitHub Pull Request 생성이나 별도 브랜치 생성을 의미하지 않는다.
- 별도 브랜치와 실제 GitHub PR은 사용자가 명시적으로 요청할 때만 사용한다.
- 사용자가 코드 반영을 요청하거나 승인한 경우 기본 브랜치에 직접 커밋할 수 있다.
- 배포는 사용자가 별도로 승인하거나 요청한 경우에만 진행한다.

### 3. 사용자 중심 개발
- AI는 개발 보조자이며 최종 설계 및 코드 반영의 결정권은 사용자에게 있다.
- 빠른 코드 생성보다 사용자가 코드를 해석하고 이해하며 개발 과정을 따라가는 것을 중시한다.
- 사용자가 직접 구현하려는 부분은 설계, 구현 순서, 핵심 예제, 코드 리뷰를 우선한다.

### 4. 검증 및 기록
- 구현 완료, 미구현, 검증 필요 항목을 구분한다.
- 실행하지 않은 테스트를 완료했다고 보고하지 않는다.
- 실제 커밋을 수행한 경우 커밋 식별자와 변경 내용을 보고한다.
